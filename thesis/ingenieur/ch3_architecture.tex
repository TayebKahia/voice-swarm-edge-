\chapter{Architecture and design}
\label{chap:architecture}

Section~\ref{sec:safety-problem} reduced the safety problem to three requirements: a wrong
command must be hard to act on, a stopping command must be fast to act on, and the execution of
any command must be bounded at the point where it takes effect. This chapter turns the first two
into a design; the third is a property of the swarm controller and is realised in
Chapter~\ref{chap:implementation}. Section~\ref{sec:dual-path} divides the runtime into two paths
that read one audio stream. Section~\ref{sec:membership-rule} derives the rule deciding which
utterances may take the fast path, and Section~\ref{sec:validation-layers} specifies the three
checks the slow path's output must pass. Sections~\ref{sec:latency-budget}
and~\ref{sec:resource-allocation} then give each stage a latency target and each path its own
processor cores, so that recognition and decoding are never scheduled on the core that serves the
reflex path. Every figure in this chapter is a design target, fixed before any measurement;
Chapter~\ref{chap:validation} measures the system against them.

\section{Dual-path decomposition}
\label{sec:dual-path}
The runtime consists of two paths that read the same audio stream and publish to the same command
bus (Figure~\ref{fig:architecture}), the reflex path and the parse path of
Section~\ref{sec:operational-context}. The reflex path is a two-class keyword spotter~\cite{oww}
that listens continuously and, on detecting either stopping phrase, publishes a fixed command
without transcribing anything. The parse path is the general path: a \gls{vad} model~\cite{silero}
segments the stream into utterances, \texttt{whisper.cpp tiny.en}~\cite{whisper,whispercpp} performs
\gls{stt} on each, a fine-tuned \gls{slm} parses the transcript into a structured \gls{json} command
under a decoding grammar~\cite{llamacpp}, and a semantic validator checks the result before it is
published.
The two paths share nothing between the audio buffer and the bus. They are not a fast and a slow
setting of one pipeline. The parse path cannot begin transcribing until the endpointer has
confirmed that the operator has stopped speaking, and that wait alone exceeds the 150~ms reflex
budget (Section~\ref{sec:latency-budget}); a stopping command on the parse path therefore misses
the reflex budget however the rest of the path is tuned (Section~\ref{sec:engineering-requirements}).
The decomposition follows from that constraint rather than from a preference for redundancy. It
borrows the distinction between a reflex and cortical deliberation: two stimuli receive a fixed
response without being interpreted, and everything else is understood before it is acted on. The
analogy stops at one point. A spinal reflex acts before the brain is consulted, whereas the reflex
path skips only transcription and parsing: its commands are checked by the validator and the state
machine like any other (Section~\ref{sec:membership-rule}).

The language model on the parse path is Qwen2.5-0.5B~\cite{qwen25}, fine-tuned and quantised to
Q4\_K\_M, a mostly 4-bit weight format of \texttt{llama.cpp}. The \emph{M\'emoire de Master}
selects this configuration by comparing models and quantisation levels on the same device; the
present document treats the choice as fixed and designs the runtime around it.

\paragraph{Placement.} Everything up to and including the command bus runs on the
Raspberry~Pi~5. The flight state machine, the swarm controller and the simulated aircraft run on a
workstation. The split follows the claim under test: this document asks whether perception and
language understanding fit on the edge device, not whether a physics engine does. A simulator
sharing the Pi's four cores would contend for the cores that Section~\ref{sec:resource-allocation}
allocates to the pipeline, and every latency figure would then depend on the simulator's load as
well as on the pipeline. With the simulation off the device, latency measured on the Pi is a
property of the pipeline alone. The state machine is placed beside the controller rather than
beside the parser because two of its transitions, reaching the take-off altitude and making
ground contact, are observations of the vehicles, and only the controller's side of the bus
makes them.

\paragraph{Command bus.} The two machines are joined by a minimal publish--subscribe bus
carrying single-line \gls{json} messages over \gls{udp}. Each message carries a command, a tag naming
the path that produced it, and a sequence number drawn from one monotonic counter shared by both
paths. The bus implements nothing else. The rule deciding whether a message may take effect
belongs to its consumer, beside the state machine, and messages from both paths reach the state
machine by that same route; a reflex-path message differs from a parse-path message only in that
it is a constant, never the output of a decoder. The bus sits behind an interface so that a
distributed middleware can replace it in a deployment beyond simulation. Adopting one here would
add failure modes of its own, such as peer discovery and network partition, to a system whose
experiments are not designed to measure them.

\paragraph{Prompt and prefix.} The command schema is not described in the prompt. Fine-tuning
teaches the model the command format, so the prompt carries only a fixed system instruction and
the transcript, and the fixed part is identical for every request. The design keeps that fixed
part resident in the model's key--value cache between requests, so that prefill for each command
processes only the transcript's tokens. The design estimate is roughly 15 tokens per command,
against roughly 290 if the schema had to be restated in every prompt, and it is the reason a
512-token context window suffices. The deployed parser departs from this assumption, for a reason
given in Chapter~\ref{chap:implementation}; the latency budget of Section~\ref{sec:latency-budget}
is stated as designed.

\paragraph{Preemption and ordering.} When the reflex path fires while the parse path is decoding,
two actions follow, and only one of them is needed for correctness. The needed one is an ordering
rule: the consumer discards any parse-path message whose sequence number is lower than that of the
latest reflex-path message already applied. A parse-path command that was being decoded when the
operator said \emph{swarm hold} therefore cannot take effect after the hold, whether or not its
decode was stopped. The rule depends on when a sequence number is assigned. A parse-path utterance
reserves its number when it is accepted for processing, before transcription begins, and not when
its decode completes. A number assigned at completion would make a slow decode that finishes after a
later trigger compare as newer than the trigger, and the stale command would override the stop the
rule exists to protect. The rule covers the utterance in progress when the trigger fires, not those
waiting behind it. An utterance that has been endpointed but is queued behind the one in progress
reserves its number only when the parse path takes it up, so it compares as newer than a trigger
spoken after it. After an abort this has no effect, because the swarm has left flight and the state
machine rejects any later motion; after a hold, which leaves the swarm flying, the queued command is
legal and takes effect (Section~\ref{sec:limitations}). The second action is an optimisation: the
decode in progress is cancelled, so that the three inference cores are released at once rather than
spent on a result that will be discarded. Correctness does not depend on the cancellation
succeeding. What the cancellation governs is recovery, the time before the parse path can accept
the next utterance, which the preemption-recovery criterion bounds at 300~ms at p95
(Table~\ref{tab:nonfunctional-requirements}). The cancellation reaches only a decode already in
progress. A trigger that arrives while the utterance is still being transcribed leaves the
transcription, and the decode that follows it, to run to completion before the ordering rule
discards the result; in that case recovery is bounded by the remaining parse-path stages, not by
the cancellation, and can exceed the criterion (Section~\ref{sec:limitations}).

\section{Reflex-path membership rule}
\label{sec:membership-rule}
The reflex path bypasses the stages that interpret speech, not the stages that check commands. Its
commands enter the same consumer as the parse path's and pass the semantic validator and the state
machine like any other message; what they bypass is transcription and parsing, the two stages that
establish what the operator said. The consequence is that no layer can detect a false accept. A
spurious trigger publishes \texttt{\{"intent":"hover"\}}, which is well-formed, inside the physical
envelope and legal while the swarm is taking off or flying: it is indistinguishable, at every check
the architecture has, from a hold the operator asked for. The layers of
Section~\ref{sec:validation-layers} test the form, range and legality of a command, and a false
accept on the reflex path fails none of those tests, because the error lies in whether the command
was spoken at all. Because the spotter listens continuously, every class it carries is a standing
source of such errors. The only protection is therefore to restrict which commands the path may
carry, and the membership rule does so with two tests, both of which a command must pass.

\paragraph{Latency-decisive.} The first test asks whether the time the reflex path saves changes the
physical outcome. The difference between the parse budget and the reflex budget is $2{,}500 - 150 =
2{,}350$~ms (Table~\ref{tab:nonfunctional-requirements}). At the validator's speed ceiling of
2.0~m/s, that interval is 4.7~m of travel, comparable to the largest formation radius the envelope
admits (10~m) and larger than every admissible inter-drone spacing (1--5~m). A stop that arrives
through the parse path can therefore arrive after a vehicle has already covered the distance the
stop was meant to prevent. A command passes this test only if that delay matters to what the
vehicles do.

\paragraph{Fail-safe under false accept.} The second test asks what happens when the command is
executed without having been spoken. A command passes only if its unprompted execution moves the
swarm towards a safer state: the reflex path may make the swarm do less, never more. This is the
test that answers the problem stated at the opening of this section, since a false accept of a command that
passes it costs an unnecessary stop and nothing else.

Neither test is sufficient alone. The first alone would admit any urgent movement, and a false
accept of an urgent movement is uncommanded motion with no stage behind it able to recognise the
error. The second alone would admit commands that are harmless but gain nothing from the fast
path, and each of them would enlarge the false-accept surface for no benefit, because the
keyword false-accept budget is aggregated over every reflex-path class. Table~\ref{tab:membership}
applies both tests to the ten intents of the schema. Exactly two pass.

The two admitted classes map onto intents the schema already contains, so the reflex path adds no
grammar rule, no schema field and no controller entry point. \texttt{swarm hold} publishes
\texttt{hover}: lateral motion stops, altitude is held, the rotors keep running, and the mission can
be resumed. The hover is already the state every rejection on the parse path resolves to where the
flight state permits it (Section~\ref{sec:validation-layers}), so the reflex makes the system's
existing safe state reachable at reflex speed rather than introducing a new one. \texttt{swarm
abort} publishes \texttt{abort}, defined as an immediate descent in place with the motors stopped on
ground contact; the mission ends and cannot be resumed by voice. Two other definitions were
rejected. Stopping the motors in flight, anywhere in an altitude envelope of 0.5--15~m, is a
decision to lose the airframe. A return to the launch point requires flight, which is what the
command exists to stop. Descending in place removes energy from the situation without lateral
motion, and it keeps the two classes distinct in effect: a hold stays airborne and an abort comes
down.

Both phrases are two words with a common prefix rather than single words. A keyword classifier
scores a fixed window of audio~\cite{oww}. The design assumes that a single short word, which
fills little of that window, gives the classifier less evidence and so invites more false accepts
on continuous speech. The assumption is not tested against a one-word alternative;
Section~\ref{sec:keyword-spotter-evaluation} reports the false-accept rate of the two phrases as
deployed. The shared word \emph{swarm} brings the two classes closer acoustically, which raises
the chance of one being heard as the other. That confusion is benign by construction: hearing \emph{abort}
for \emph{hold} is the more conservative error, and hearing \emph{hold} for \emph{abort} still
stops the swarm. Because both classes passed the second test, an error between them stays within
the set of fail-safe outcomes.

The most obvious third class is excluded deliberately. A \texttt{resume} phrase would be as
urgent to the operator as any other, but a false accept would restart motion the operator had
chosen to freeze, which reverses a safety action rather than adding one. It fails the second test,
and resumption is therefore available only through the parse path, where the added 2.35~s costs
nothing. Recovery out of an abort is not available by voice on either path, for the same reason
(Section~\ref{sec:validation-layers}).

\enlargethispage{\baselineskip}%
The rule states the condition under which a third class could be admitted: its command passes
both tests, and the false accepts it adds fit within the aggregate budget measured with it in
place. The tests apply to the command a phrase publishes, not to the phrase, so a change of
wording cannot admit a command the rule excludes, and they are applied again whenever the schema
gains an intent. For the present vocabulary the rule yields exactly two classes; that result, and the rule that
yields it, are the second clause of the contribution of this document
(Section~\ref{sec:contributions}), and they are what make the membership of the reflex path
checkable by a reader who did not choose it.

\section{Three validation layers}
\label{sec:validation-layers}
Three layers stand between a decoded command and the vehicles, and each checks a property the one
before it cannot: the grammar fixes the form of a command, the semantic validator its meaning and
magnitude, and the flight state machine its legality in the swarm's current state. The second and
third layers apply to every command from either path; the reflex path's commands are constants of
the command language and pass through them like any other message. The first applies only to the
parse path, because it acts on the decoder while the command is being produced.

\paragraph{Layer 1: the decoding grammar.} The command schema and the grammar that enforces it are
specified, with the grammar in full, in the \emph{M\'emoire de Master}; this document relies on
three of their properties. Every complete decode is a string of the command language: single-line
\gls{json} with one of ten intents and a fixed key order, so a structurally invalid command is
unreachable rather than improbable; only a decode cut off at the token limit can be malformed, and
the validator's fallback catches it. The grammar bounds the length of every number, at three
integer digits and one decimal place, and it restricts drone identifiers to the five that exist.
It does not bound a number's value: the \emph{M\'emoire de Master} explains why a range is not
encoded in the grammar, and the consequence here is that an out-of-range value reaches the second
layer, which clamps it and logs the change. Every constraint on magnitude therefore falls to the second layer.

\paragraph{Layer 2: the semantic validator.} The validator applies four rules. The first
enforces the slots each intent requires: a formation needs a shape, a circle a radius, and a line,
grid or column a spacing; an altitude command needs a target height, a rotation an angle, and a
movement either a position or a direction with a distance, never both. The second enforces the
physical envelope by clamping and logging, never by rejecting. A radius is clamped to 1--10~m, a
spacing to 1--5~m, a target height to 0.5--15~m, a speed to 0.2--2.0~m/s and a distance to at
most 50~m. A target position has its height clamped to 0.5--15~m, like a target height; if it
then lies more than 50~m from the origin, its horizontal part alone is scaled down until it does,
so that the commanded bearing survives the clamp, where clamping each horizontal component
separately would rotate it. A yaw angle is wrapped into $[-180^\circ, 180^\circ]$ rather than clamped, because
angles are periodic and $270^\circ$ and $-90^\circ$ are the same heading. The third rule keeps only
identifiers of drones that exist and removes duplicates. Under the grammar an identifier outside
the swarm cannot be decoded, so on the parse path this rule only removes duplicates. The fourth
rule is the fallback: a missing slot, output that does not parse, or a decode cut off at the token
limit resolves to a hold with a structured log entry, and never to a substituted movement.
An abort is never weakened by this rule: an abort carrying a superfluous slot has the slot dropped
and remains an abort.

Clamping rather than rejecting is a choice about which error to prefer. A command whose intent is
right and whose magnitude is out of range, such as a climb to a height above the ceiling, is
executed at the nearest admissible value instead of being replaced by a hold that the operator did
not ask for. Its cost is the first class of error named at the end of this section.

\paragraph{Layer 3: the flight state machine.} A command can be well-formed and within the
envelope and still be wrong for the moment it arrives: a movement while the swarm is on the
ground, or a take-off while it is already flying. The state machine tracks five states:
\texttt{LANDED}, \texttt{TAKING\_OFF}, \texttt{FLYING}, \texttt{LANDING} and \texttt{ABORTED}. A
take-off moves the swarm from \texttt{LANDED} to \texttt{TAKING\_OFF}, and reaching the target
height moves it on to \texttt{FLYING}. A landing command moves it from either of those states to
\texttt{LANDING}, and ground contact completes the landing. An abort moves it from any airborne
state to \texttt{ABORTED}. Table~\ref{tab:legality} gives, for each intent, the states in which the
state machine admits it.

A rejection is resolved according to whether a hold is itself legal in the current state. While
the swarm is taking off or flying, a rejected command becomes a hold with a log entry. On the
ground, during a landing and after an abort, a hold is not legal either, and dispatching one would
spin up grounded rotors, stop a descent at altitude or return an aborted swarm to flight; a
rejection there is therefore a logged no-op. The same rule applies to the reflex path: a
\emph{swarm hold} spoken while the swarm is landed is logged and has no effect. Recovery out of
\texttt{ABORTED} is not a command at all. It is a manual reset, outside the voice interface,
which returns the state machine to \texttt{LANDED} only once every drone reports ground contact
and near-zero velocity, and it writes a record of the reset to the log. Because no utterance on
either path can leave \texttt{ABORTED}, a misheard word on either path cannot undo an abort. The hold the validator substitutes for output
it cannot accept is itself a command and passes this layer, so on the ground, during a landing and
after an abort it too becomes a logged no-op. A decode cancelled by the reflex path publishes
nothing.

\paragraph{Residual error classes.} Two classes of error pass the layers, and both follow
from the design rather than from a defect in it. The first is a value outside the envelope. It is
clamped to the envelope's bound and executed, so the motion it produces is bounded but not
withheld: a misrecognised height above the ceiling becomes a climb to the ceiling. The second is a
command that is well-formed, within the envelope and legal in the current state, yet not the
command the operator gave. It passes all three layers unchanged, because each layer tests a
property of the command and none can test whether it matches what was said. A rotation through the
right angle in the wrong direction is one example; a slot value misheard within its range and a
wrong intent that happens to be legal are others. A false accept on the reflex path belongs to the
same class, which is why Section~\ref{sec:membership-rule} restricts what that path may carry
rather than relying on the layers to catch it. How often errors fall into these classes rather
than resolving to a hold is what the safe-failure rate measures, and
Section~\ref{sec:acoustic-robustness} reports it.

\paragraph{Anchors.} Each path is measured from two instants, because either one alone misleads.
On the parse path, $T_0$ is the time of the last audio sample the endpointer has processed at the
moment it declares the utterance over, and the headline target of 2{,}500~ms runs from it.
Measured only from $T_0$, the system would appear to respond independently of how long the
operator spoke; measured only from the start of speech, it would be charged for the length of
the operator's sentence. Both are therefore reported. The reflex path's headline anchor is the
keyword offset, the last frame of the spoken phrase. An onset-anchored target of 150~ms could not
be met by any spotter, because a phrase of about 700~ms cannot be classified before it has been
heard. The offset anchor isolates what the system adds: feature extraction, the classifier, the
spotter's decision delay (the frames after the offset before its score crosses the detection
threshold), the quantisation of audio into 80~ms frames, and publication on the bus. These parts
are not budgeted separately; the 150~ms span bounds their sum. The onset figure is reported
beside it as the time the operator perceives. Both spans end when the command is handed to the
command bus on the device, which is the last point both paths have in common.

\paragraph{Endpointing.} The first parse-path row is not a processing time but a wait: the
endpointer declares an utterance over only after a run of silence, and the clock of the
end-to-end target starts when that declaration is made. The wait is therefore budgeted as a row of
its own, at 500~ms, and the endpointer's silence rule was derived from that row rather than tuned.
Silence is counted in whole windows of 32~ms, so the wait is the silence threshold plus at most one
window. The threshold is the largest round value for which that sum stays inside the allowance:
450~ms, for a worst case of 482~ms. A shorter threshold answers sooner and splits more utterances
at a pause; this one was set by the budget and not by that trade, and
Section~\ref{sec:acoustic-robustness} reports what it costs in recognition.

\paragraph{Stage allowances.} Transcription and decoding are each allowed about a second, and they
dominate the parse path. The decode allowance is sized for the short wire format of the command
schema, in which absent slots are omitted rather than written as nulls. The prefill allowance of
250~ms assumes the cached fixed prefix of Section~\ref{sec:dual-path}, which reduces prefill to the
transcript's own tokens. The two language-model rows together allow 1{,}350~ms, and the
\emph{M\'emoire de Master} applies that combined figure as the deployment constraint of its model
comparison. The allowances are ceilings, not shares of the end-to-end target. The four that follow
$T_0$ sum to 2{,}600~ms, more than the 2{,}500~ms they sit inside, so a run in which every stage
reaches its ceiling at once misses the end-to-end target. That target is judged on the measured
end-to-end figure, never on the sum of the stage figures, and the stage rows serve to locate a
miss, not to excuse one.

\paragraph{Outside the budget.} Two delays fall outside the table by design. Capture and buffering
sit before $T_0$: the time from sound reaching the microphone to its frame entering the buffer is a
property of the audio hardware, not of the pipeline, and it is excluded so that the budget
describes what the pipeline adds. The wireless hop from the device to the workstation sits after
publication, and it depends on the link rather than on the device. The state-machine check that
the deployed placement puts on the far side of that hop is budgeted within the 50~ms row, but
the end-to-end spans stop at the bus.

\section{Resource allocation}
\label{sec:resource-allocation}
The reflex latency criterion must hold while the parse path is decoding
(Table~\ref{tab:nonfunctional-requirements}), so the two paths cannot be left to compete for the
processor. The Raspberry~Pi~5 has four Cortex-A76 cores, and the design divides them between the
paths as Table~\ref{tab:core-allocation} sets out: one core for everything that must keep pace with
the audio, and three for the work whose cost depends on the utterance.

\begin{table}[htbp]
\centering
\footnotesize
\caption[Core allocation]{Allocation of the Raspberry~Pi~5's four cores. Core~0 runs the audio
frame loop, which includes the reflex path and the parse path's endpointer. No work of the
parse-path worker (speech recognition, decoding, validation) is scheduled on core~0.}
\label{tab:core-allocation}
\begin{tabularx}{\textwidth}{@{}l X X@{}}
\toprule
Cores & Assigned work & Constraint the assignment must meet \\
\midrule
0 & Audio frame loop: frame buffering, the endpointer, the keyword spotter and the reflex path's publication & The work for one 80~ms frame completes within 80~ms, on every frame \\
1--3 & Parse-path worker: speech recognition and the language model, each on three threads, then validation and publication & Speech recognition and the language model never run at the same time \\
\bottomrule
\end{tabularx}
\end{table}

\paragraph{Core 0.} The frame loop takes one 80~ms frame at a time and gives it to both the
endpointer and the keyword spotter. It never waits for the parse path: an endpointed utterance is
handed to the worker on cores~1--3, and the loop moves on to the next frame. This is the property
the reflex latency criterion depends on. If the loop could wait for a transcription or a decode, a
keyword spoken during one would be heard only after it finished, and the reflex would inherit the
parse path's latency, which is the failure Section~\ref{sec:dual-path} exists to avoid. The
constraint on core~0 is correspondingly strict. The work for each frame must complete within the
frame's own duration, on every frame, or the loop falls behind the audio and every later keyword is
heard late.

\paragraph{Cores 1--3.} Speech recognition and the language model share three cores without
contending for them, because they are sequential by construction: the parser cannot start before
the transcript exists. Each therefore runs on all three cores in turn, and a three-core allocation
serves both. These are also the cores that the cancellation of Section~\ref{sec:dual-path}
releases: when the reflex path cancels a decode, they become free for the next utterance.

\paragraph{Limits of core pinning.} Pinning separates the paths' computation, not everything
the four cores share. Memory bandwidth, the shared cache and the device's temperature are common to
all of them, so parse-path work can still slow core~0 without being scheduled on it. The
allocation therefore reduces the interference between the paths to what these shared resources
carry. Whether that remainder stays inside the reflex budget is not a design property, and the
loaded condition of the latency experiment (Section~\ref{sec:latency-experiment}) measures it.

\paragraph{Memory.} Memory is not divided between the paths. Every stage shares the device's
8~GB, and the constraint that governs it is the 2.5~GiB ceiling on the full deployed stack, which
the \emph{M\'emoire de Master} states and assesses for its model comparison. That document measured
the memory of the language-model process only; the full stack was not measured for any
configuration, and this design adds no estimate that would stand in for that measurement.

This chapter has fixed the two paths, the rule that bounds the reflex path, the three validation
layers, the latency budget and the allocation of the processor.
Chapter~\ref{chap:implementation} describes how each is built and where the built system departs
from the design, including the parser's uncached prefix (Section~\ref{sec:runtime}).
