\section{Command schema and grammar design}
\label{sec:schema}
The schema is the contract Section~\ref{sec:constrained-decoding} in Chapter~\ref{chap:related-work}
argued for: a fixed vocabulary of structured commands that a flight controller can act on directly,
with every property a controller depends on enforced before a command is dispatched rather than
checked afterwards. It was frozen before any data generation began, on the project's first
development day, so that no later convenience -- an intent that turned out to be hard to elicit
paraphrases for, a slot that turned out to be hard to fine-tune -- could reshape the target the
whole pipeline is built against. Ten intents cover the vocabulary: \texttt{formation},
\texttt{move}, \texttt{altitude}, \texttt{takeoff}, \texttt{land}, \texttt{hover}, \texttt{abort},
\texttt{rotate}, \texttt{set\_param}, and \texttt{unknown}, the last of which is the schema's only
provision for an utterance that does not map onto a command at all.

The wire format is single-line JSON with a key order fixed by the schema declaration and null or
absent slots omitted rather than emitted explicitly:

\begin{lstlisting}[basicstyle=\ttfamily\small, breaklines=true]
{"intent":"formation","shape":"circle","radius":5.0}
{"intent":"move","pos":[10.0,0.0,3.0],"speed":1.5}
{"intent":"move","dir":"north","dist":10.0}
{"intent":"altitude","z":4.0,"ids":[1,2]}
{"intent":"rotate","yaw":90.0}
{"intent":"set_param","speed":1.0}
{"intent":"hover"}
{"intent":"abort"}
{"intent":"unknown"}
\end{lstlisting}

Omitting null fields is not a stylistic choice; it is a latency decision. A representative command
written with every field present, nulls included, runs to roughly 40 tokens; the same command in
this wire format runs to about 18. At the Raspberry~Pi~5 decode rates this document works against --
a margin of single-digit tokens per second above the 20~tok/s floor -- the difference
between 40 and 18 tokens is close to a full second of decode time per command, recovered without
touching the model. It is the second-largest latency saving in the system, after keeping the schema
itself out of the prompt.

Three layers guarantee, in sequence, that a command reaching the flight controller is
well-formed, physically sensible, and legal for the aircraft's current state. This chapter owns
only the first of them; the second and third are validator and state-machine layers that consume
the schema and grammar defined here but belong to the \emph{M\'emoire d'Ing\'enieur}'s architecture
chapter, which is where their design and their contribution to the safety argument are discussed
in full.

\paragraph{Layer 1 --- GBNF grammar.} A context-free grammar in the GBNF (GGML BNF) formalism,
compiled once and used by llama.cpp to mask the decoder's token distribution at every decoding
step~\cite{llamacpp}, is generated directly from the schema so the two cannot drift apart:

\begin{lstlisting}[basicstyle=\ttfamily\footnotesize, breaklines=true]
root      ::= cmd
cmd       ::= c-form | c-move | c-alt | c-takeoff | c-land | c-hover | c-abort | c-rot | c-param | c-unk

c-form    ::= "{\"intent\":\"formation\",\"shape\":" shape o-radius o-spacing o-ids "}"
c-move    ::= "{\"intent\":\"move\","  ( kv-pos | kv-dir ) o-speed o-ids "}"
c-alt     ::= "{\"intent\":\"altitude\",\"z\":" num o-ids "}"
c-takeoff ::= "{\"intent\":\"takeoff\""  o-z o-ids "}"
c-land    ::= "{\"intent\":\"land\""     o-ids "}"
c-hover   ::= "{\"intent\":\"hover\""    o-ids "}"
c-abort   ::= "{\"intent\":\"abort\"}"
c-rot     ::= "{\"intent\":\"rotate\",\"yaw\":" num o-ids "}"
c-param   ::= "{\"intent\":\"set_param\"" o-speed o-spacing o-alt "}"
c-unk     ::= "{\"intent\":\"unknown\"}"

shape     ::= "\"circle\"" | "\"line\"" | "\"wedge\"" | "\"grid\"" | "\"column\"" | "\"flock\""
dir       ::= "\"north\"" | "\"south\"" | "\"east\"" | "\"west\"" | "\"up\"" | "\"down\"" | "\"forward\"" | "\"back\"" | "\"left\"" | "\"right\""

kv-pos    ::= "\"pos\":[" num "," num "," num "]"
kv-dir    ::= "\"dir\":" dir ",\"dist\":" num

o-radius  ::= ( ",\"radius\":"  num )?
o-spacing ::= ( ",\"spacing\":" num )?
o-speed   ::= ( ",\"speed\":"   num )?
o-alt     ::= ( ",\"alt\":"     num )?
o-z       ::= ( ",\"z\":"       num )?
o-ids     ::= ( ",\"ids\":[" idlist "]" )?
idlist    ::= [0-9] ( "," [0-9] )*

num       ::= "-"? [0-9] [0-9]? [0-9]? ( "." [0-9] )?
\end{lstlisting}

The \texttt{num} rule bounds every numeric field to three integer digits and one decimal place,
which is what makes \texttt{1e999}, a twenty-digit integer, or a bare trailing decimal point
structurally unreachable rather than merely unlikely -- no value of that shape is in the grammar's
language, so the decoder cannot sample toward one regardless of what the model's own distribution
would otherwise favour. GBNF has no way to express a numeric \emph{range}: a grammar can bound how
many digits a number has, not whether $91.0$ is a legal yaw. Range enforcement is therefore left to
Layer 2, and the one-decimal digit limit fixed here is also why the canonical comparator defined in
Section~\ref{sec:definitions-of-record} rounds every numeric slot to one decimal before comparison --
the metric is built to match what the decoder can actually produce, not a precision the schema never
promised.

The distinction this design rests on -- between a rate that a favourable test set and thorough
fine-tuning can inflate, and a property that holds by construction on any input, in or out of
distribution -- is the argument Section~\ref{sec:constrained-decoding} already made in the
abstract. Chapter~\ref{chap:results} makes it concrete: Table~19 reports the same fine-tuned model
decoded with and without this grammar, isolating what the grammar contributes once fine-tuning has
already done most of the work of keeping output well-formed.

\section{Label-first dataset construction}
\label{sec:dataset}
No corpus existed for this vocabulary before this project, so the dataset that trains and
evaluates every model in Chapter~\ref{chap:results} had to be built rather than assembled from an
existing resource, which is the labour Contribution~C2 names. It is built and sealed under a
single governing decision: generation runs \textbf{label first}. The target JSON is written before
any sentence exists, and natural-language phrasings are then elicited for it -- eight per label for
the synthetic corpus -- rather than the reverse order of writing sentences and labelling them
afterwards. The reverse order reintroduces the annotation cost this pipeline exists to remove, and
it produces the label noise that comes with a human resolving ambiguous cases at scale; writing the
label first makes the label the source of the data rather than a judgement made about it.
Table~\ref{tab:dataset} lists every component this document's experiments and the companion
runtime consume, with the role that motivates each one.

\paragraph{Synthetic generation and splits.} Diversity in the synthetic corpus is enumerated
explicitly rather than left to sampling temperature, along axes chosen to cover the ways a command
is actually spoken: imperative and polite forms, unit variants (metres, m), numeric forms (five,
5, 5.0), drone subsetting (all drones, drone two, drones one and three), synonym sets per intent,
filler words, self-corrections, and truncated utterances. Splits are assigned by
\textbf{template family}, not by row: every paraphrase descended from the same label lands in the
same split, because a row-wise split would place near-duplicate paraphrases of one label on both
sides of the train/test boundary and inflate every accuracy figure that follows. \texttt{check\_leakage.py}
enforces this partitioning as a gate rather than a report, checking family, surface-form, and
eval-independence isolation together with the wake-corpus and noise-partition isolation described
below; all four axes are clean. A second, independent gate -- the \textbf{conformance assert} --
checks every label in every split against \texttt{cmd.gbnf} (Section~\ref{sec:schema}) before it
is accepted into the dataset, because a label the grammar itself cannot produce would be an
unreachable target that silently caps the accuracy any model could ever reach against it.

\paragraph{Audio: bulk synthesis and the golden set.} Bulk training and validation audio is
synthesised with Piper text-to-speech~\cite{piper}, mixed with noise at four signal-to-noise
levels, and passed back through \texttt{whisper.cpp}~\cite{whispercpp} in a round-trip: the training
data is built from what the automatic speech recogniser actually transcribes, transcription errors
included, rather than from the clean text a model will never see at inference time. The evaluation
set that anchors every headline accuracy figure is different in kind: a single-speaker
\textbf{golden set}, the author reading 200 utterances in a quiet room, covering all ten intents
and every slot combination the required-slot matrix admits, recorded once and never re-synthesised.
The original protocol called for two further sessions on the same 60-utterance subset -- a
different room with real background noise, and the same room again on a different day, to capture
voice variation across time -- and both were cut under the build schedule this project executed
against; the companion document states the consequence of that cut for its own runtime validation
as a limitation. The signal-to-noise sweep Chapter~\ref{chap:results} reports over is
unaffected by the cut: it is mixed \emph{digitally} from this single session's clean recording, so
noise remains the only variable Exp-3 varies and no additional session was ever needed for that
comparison. What the cut removes is a claim this document does not make in either case: holding the
speaker fixed at one session is an internal-validity choice, not an external one, and speaker
generalisation is recovered separately, at the acoustic-model stage, by Exp-0 against
\texttt{commonvoice} rather than by a second or third session of the same speaker.

\paragraph{Noise and annotation.} The noise corpus mixed into training and evaluation audio is
named with its licence and provenance in the dataset card: ESC-50~\cite{esc50} for environmental
sound classes and DREGON~\cite{dregon} for UAV-embedded rotor noise, mixed by the single, seeded
path \texttt{data/mix\_noise.py}. Signal-to-noise ratio is computed on active-speech level against
noise RMS rather than full-file RMS, because full-file RMS lets leading silence set the level and
makes the nominal ratio depend on how promptly a speaker starts talking. Annotation quality is
examined, not assumed: the author labels 50 golden-set utterances, five per intent, seals that pass
under SHA-256 on the day of recording, then relabels the same 50 items in a different random order
after an interval, with neither the sealed pass nor the generated targets visible. No agreement
rate is computed from this exercise -- at a short interval, a matching pair of labels is as easily
recall as schema clarity, so a percentage would measure memory rather than ambiguity. What is
reported instead is the list of items the two passes label \emph{differently}: recall can only push
two passes together, never apart, so a disagreement is evidence that the schema admits two readings
regardless of the interval length, and the count is a lower bound rather than a claim of
completeness. \TODO{disagreement count and items from annotation pass 2, \texttt{data/annotate.py --compare}}

\paragraph{The wake corpus.} \texttt{wake\_pos} and \texttt{wake\_neg} are built for the companion
document's Branch~A keyword spotter and are described here because they share this chapter's
construction pipeline, not because this document's own experiments consume them. Positive clips
are synthesised with Piper and passed through openWakeWord's own training pipeline~\cite{oww},
with the keyword placed at a random offset within the clip rather than centred, and forty
near-miss phrases authored by hand, since no public corpus contains the words ``swarm'' or a
phrase beginning with ``hold.'' Splits are assigned by base rendition (70/10/20) for positives, by
speaker for negatives, and by phrase for near-misses, so that a held-out item differs from every
training item along the axis that would otherwise let a spotter memorise a specific recording
rather than the keyword itself; held-out clips are also mixed with room impulse responses and noise
drawn from a disjoint 70/30 augmentation/evaluation partition, recorded per clip as
\texttt{noise\_partition}, so a spotter cannot be evaluated on the exact acoustic conditions it was
augmented against.

\paragraph{Common Voice.} The Exp-0 speaker-sensitivity baseline draws 300 clips from an ungated
mirror of Mozilla Common Voice release 17.0~\cite{commonvoice}, stratified across fifteen accent
buckets spanning 263 speakers rather than sampled uniformly, since a uniform draw over the corpus
is 39\% United States English and would answer a question about one accent rather than about
speaker variation in general.

\section{The LoRA recipe}
\label{sec:lora}

accuracy difference Chapter~\ref{chap:results} reports is attributable to the model rather than to
an uncontrolled difference in how it was trained: Qwen2.5-0.5B-Instruct~\cite{qwen25},
SmolLM2-360M-Instruct~\cite{smollm2}, and Llama-3.2-1B-Instruct~\cite{llama32}, spanning the
0.36--1.2~B range RQ1 asks about. Table~\ref{tab:lora} fixes every setting.

\paragraph{LoRA, not QLoRA.} Low-rank adaptation~\cite{lora} freezes the base weights and trains a
pair of rank-$r$ update matrices per targeted projection, which is sufficient on its own to bring
a 0.36--1.2~B model to convergence on a vocabulary this narrow. QLoRA adds one further step --
quantising the frozen base weights during training, to fit a larger model into a smaller training
budget -- and every model here is already small enough to fine-tune in full precision on the
training hardware available, so that step would add a training-time quantisation confound without
recovering any memory the training run needs. The rank-16 adapters target every linear projection
in the transformer block, attention and feed-forward alike, rather than attention alone, on the
same reasoning that motivates the schema in Section~\ref{sec:schema}: a narrower adapter would risk
under-fitting a vocabulary this precise rather than saving a memory budget the training hardware
does not require saving.

\paragraph{Completion-only masking.} The loss is computed only over the tokens the model is asked
to produce -- the JSON command -- and the prompt tokens that precede it, transcript and schema
instructions alike, contribute no gradient. Training on the prompt as well would reward the model
for reproducing input it is never asked to generate at inference time, diluting the gradient signal
with tokens that carry no information about whether the command that follows is correct.

\paragraph{Checkpoint selection.} The checkpoint kept from each run is the one with the highest
exact match on \texttt{val\_synth} (Table~\ref{tab:dataset}), not the one with the lowest validation
loss. Cross-entropy loss is computed token-by-token and rewards partial credit for a JSON output
that is close in a token sense but wrong in the sense that matters to a flight controller -- a
single incorrect digit in a coordinate can carry a small loss penalty and a complete exact-match
failure at once -- so selecting on loss would optimise a proxy the deployment does not care about
in place of the metric it does.

\paragraph{The fp16-for-bf16 deviation.} Table~\ref{tab:lora} specifies fp16, not the bf16 this
recipe originally called for, and the reason is fixed by the training hardware rather than by
choice: all three models are fine-tuned on Kaggle's free-tier GPU accelerator, an NVIDIA~T4
(compute capability~7.5, the Turing architecture). Hardware bf16 support was introduced with
Ampere (compute capability~8.0), two generations later, so the T4 has no native bf16 path for the
training run to use; every run is switched to fp16 instead, uniformly. The deviation is declared
once, here, and not repeated in Chapter~\ref{chap:results}, because it applies identically to all
three models: each is trained under the same substituted precision, on the same accelerator, with
every other setting in Table~\ref{tab:lora} held fixed, so precision is not a variable that differs
across the comparison RQ1 depends on. The ranking among the three models that
Chapter~\ref{chap:results} reports is a ranking obtained under one precision applied uniformly to
all three, not an artefact of any one model receiving a training precision the others did not.

\section{Quantisation procedure}
\label{sec:quantisation-procedure}
Each of the three fine-tuned adapters is merged into its base weights, converted to GGUF at f16,
and quantised with \texttt{llama-quantize}~\cite{llamacpp} to two levels -- Q8\_0 and Q4\_K\_M --
producing six deployable artefacts from three fine-tuning runs. Merging and GGUF conversion run on
Kaggle, alongside the fine-tuning itself, because both steps need the \texttt{torch} and
\texttt{peft} stacks that this project's environment gate keeps off the workstation entirely;
\texttt{llama-quantize} is pure C\,++ with no such dependency, so quantisation itself runs locally,
against the f16 GGUF that Kaggle produces.

\paragraph{Two measurement surfaces, never conflated.} Quantisation is measured, not assumed, by
holding two surfaces strictly apart. \textbf{Surface~A} is the fp16 merged model run on the
workstation: a reference point, useful for isolating what quantisation itself costs, but not a
configuration this project ever deploys. \textbf{Surface~B} is one of the six quantised GGUF
artefacts run on the target Raspberry~Pi~5: what actually ships, and the surface every headline
accuracy figure in Chapter~\ref{chap:results} reports from. The difference between the two,
$A - B$, is Contribution~C3 -- the accuracy cost of quantisation, reported as a measured delta
rather than assumed from the perplexity figures the quantisation literature conventionally
reports (Section~\ref{sec:quantisation}) -- and it is what Table~18 in
Chapter~\ref{chap:results} presents.

\paragraph{Chat-template parity.} Fine-tuning happens through a HuggingFace tokeniser and its
chat template; inference happens in \texttt{llama.cpp}, a separate implementation of the same
template. If the two disagree on a special token, a whitespace convention, or a role marker, the
mismatch produces no error at inference time -- the model simply decodes against a prompt shaped
slightly differently from the one it was trained on, and accuracy degrades with nothing in the
pipeline to flag why. Because this failure is silent, it cannot be left as a risk noted in passing:
\texttt{test\_template\_parity.py} compares tokenised output for ten fixed prompts across both
stacks and is run as a mandatory gate after every GGUF conversion, not as a diagnostic invoked only
when a result already looks wrong.

\section{Evaluation protocol and the definitions of record}
\label{sec:definitions-of-record}
Every accuracy number in either document traces to the functions fixed in this section, frozen
alongside the command schema before any data existed, on the same principle: a metric changed
after results exist is not a metric, it is a description of whichever result looked best.

\paragraph{Protocol.} Decoding is greedy, under the grammar of Section~\ref{sec:schema}, for every
accuracy figure either document reports -- no sampling temperature, no beam search -- which makes a
given model's output for a given input deterministic. This is also what separates the two
categories of measurement this project takes. Exact match, the F1 scores, command recognition
rate, and schema validity are computed once per test item and are therefore hardware-independent:
they are run on the workstation, and evaluating them there rather than on the Raspberry~Pi~5
changes nothing about their value, only how long they take to obtain. Latency is not
hardware-independent in the same way -- it varies with scheduling, cache state, and thermal
throttling on the specific device that ships -- so every timing figure either document reports is
measured on the target Raspberry~Pi~5 itself, never inferred from the workstation. The two
categories consequently report a different sample size for the same configuration: because
decoding is deterministic, $n_{\mathrm{accuracy}}$ is the number of test items in the split being
scored, while $n_{\mathrm{latency}}$ is the number of timed repetitions, fixed project-wide at 200
per configuration. Reporting one $n$ for both would misstate whichever of the two it was borrowed
from.

\paragraph{Canonical form and the single comparator.} A single function, $\mathrm{canon}(\cdot)$,
is applied to both the model's prediction and the reference label before either is compared to
anything, so that exact match and command recognition rate are never computed against two
differently normalised objects. Canonicalisation fixes the key order to the schema's declaration
order, omits absent or null fields rather than emitting them, rounds every float to one decimal
place -- matching the one-decimal limit the \texttt{num} rule already imposes on what the grammar
can produce (Section~\ref{sec:schema}) -- deduplicates and sorts \texttt{ids} ascending, and strips
all whitespace outside string literals. Two commands are equal if and only if their canonical forms
are byte-identical, which reduces numeric comparison to a single rule: two numeric slots are equal
if and only if $\mathrm{round}(a,1) = \mathrm{round}(b,1)$.

Exact match and command recognition rate are, by design, the same comparison applied at two
different points in the pipeline: exact match takes reference text as input, so the model is the
only variable under test and the three fine-tuned candidates can be separated from one another
cleanly; command recognition rate takes audio through the entire pipeline, automatic speech
recognition included. Because the comparator itself never changes between the two, the gap between
them on the same underlying items is attributable to a single cause -- the cost of the
speech-recognition stage -- and Chapter~\ref{chap:results} reports that gap as a finding in its
own right rather than folding it into one end-to-end number. Feeding audio to the reference-text
experiment instead would impose a shared word-error-rate ceiling on all three models at once,
compressing whatever separates them and making any remaining difference impossible to attribute to
the parser rather than to the recogniser in front of it.

Table~\ref{tab:metrics} fixes every metric either document reports; one absent from this table does
not appear in either. This document's own results (Chapter~\ref{chap:results}) draw on exact
match, the two F1 scores, schema validity, safe-failure rate, false-command rate, and throughput;
the remaining rows -- pipeline latency, formation accuracy, and convergence -- are computed by and
reported in the \emph{M\'emoire d'Ing\'enieur}, which cites the comparator and the canonical form
defined here rather than re-deriving them.
