\chapter{Implementation}
\label{chap:implementation}
This chapter describes the system as built, in the order a command travels through it: from
audio to a command on the bus, and from the bus to the simulated vehicles.
Section~\ref{sec:audio-chain} covers the audio stream both paths read, Section~\ref{sec:runtime}
the parse path and the preemption of its decode, Section~\ref{sec:command-bus} the bus, and
Section~\ref{sec:state-machine} the code that enforces the legality rules of
Section~\ref{sec:validation-layers}. Section~\ref{sec:swarm-controller} describes the swarm
controller and the separation clamp that realises the third mechanism of the safety problem
(Section~\ref{sec:safety-problem}), and Section~\ref{sec:simulation-backends} the two simulators
the controller runs under. The design of Chapter~\ref{chap:architecture} is referred to rather than
restated, and every figure in this chapter is a parameter of the code or a criterion of a test, not
a measured result; the outcomes of the automated tests that verify two criteria, the state
machine's and the backends', are stated where the tests are described. Three
components the demonstration of Chapter~\ref{chap:demonstration} requires are not built: live
microphone capture, an entry point that starts the runtime as one process, and the link from the
state machine to the swarm controller. Each is named as absent in the section where it would sit.

\section{Audio chain}
\label{sec:audio-chain}
The audio chain begins at a recorded file. The frame loop reads from a frame source, defined as
any sequence of 80~ms frames of 1{,}280 samples at 16~kHz, each paired with the instant at which
its last sample enters the buffer. The only source built replays a recorded 16~kHz file and
releases each frame at its real-time due instant, so the stages downstream receive audio at the
rate a live stream would deliver it. No microphone source exists. Live capture is the one stage of
the chain that is not built, and the demonstration (Section~\ref{sec:demonstration-protocol}) is
the first run that requires it. Because the loop consumes only frames and their due instants, a
capture source would replace the replay without a change to any stage that follows it.

\paragraph{One stream, two consumers.} The frame loop runs on one thread, pinned to core~0
(Table~\ref{tab:core-allocation}). Each frame is passed to the keyword spotter and then to the
endpointer, both on that thread. An utterance the endpointer closes is placed on a queue and taken
by a worker thread pinned to cores~1--3, which writes it as a 16~kHz mono file and runs the parse
path on it (Section~\ref{sec:runtime}). The queue is the only link between the two threads, and the
loop never waits on the worker, which is the property Section~\ref{sec:resource-allocation}
requires of core~0. For every frame the loop measures how late it picked the frame up and how long
the spotter and the endpointer took on it; the second is the quantity against which the core-0
constraint of Table~\ref{tab:core-allocation} is judged, and Section~\ref{sec:latency-experiment}
reports it. Both paths are timestamped on the wall clock. A reflex-path trigger carries the due
instant of the frame that fired it, so the quantisation of audio into 80~ms frames falls inside
the reflex latency, as the offset anchor of Section~\ref{sec:latency-budget} requires. The
endpointer reports $T_0$ in stream time, as the last sample it has passed through the \gls{vad}
model; that sample can lie up to one 32~ms window short of the end of the current frame, and the
loop subtracts the remainder when it converts $T_0$ to wall-clock time rather than taking the
frame's due instant.

\paragraph{Endpointing.} The endpointer runs the Silero \gls{vad} model~\cite{silero} on ONNX
Runtime directly, not through the package's own wrapper, because that wrapper imports
PyTorch~\cite{pytorch}, which is kept off the deployed stack. It reproduces the wrapper's
processing exactly: windows of 512 samples (32~ms), each preceded by the last 64 samples of the
window before it, with the model's recurrent state carried from one window to the next. A frame of
1{,}280 samples is not a whole number of windows, so the remainder is held until the next frame
completes it. The model runs on a single thread, since it shares core~0 with the spotter. Speech
begins at the first window whose speech probability reaches 0.5. It ends once the probability has
stayed below 0.35 for the silence threshold of 450~ms derived in Section~\ref{sec:latency-budget};
the gap of 0.15 between the two thresholds is Silero's own hysteresis, and it keeps a probability
that hovers near 0.5 from opening and closing utterances in quick succession. Each segment is
padded by 200~ms at both ends, in place of Silero's default of 30~ms, so that the first consonant
of an utterance is not cut before transcription. The padding costs no waiting time: both pads are
taken from audio already in the buffer, since the trailing pad lies within the 450~ms of silence
the endpointer has already received, and the endpointer refuses a pad longer than the silence
threshold for that reason. An utterance still open after 15~s is closed by force and marked as
such. The segments the threshold produces, including the utterances it splits at a pause, are
reported with their cost in recognition in Section~\ref{sec:acoustic-robustness}.

\paragraph{Keyword spotter.} The spotter consists of two classifier heads, one per class, over the
frozen feature front end of openWakeWord~\cite{oww}. The front end converts audio into a
mel spectrogram and then into one 96-dimensional speech embedding per 80~ms frame; each head scores
the last 16 embeddings, which span about two seconds of audio. A class detects on a frame when its
score reaches the operating threshold, which is common to both heads and fixed by training. A
spoken phrase keeps its score above the threshold for several consecutive frames, so detection is
debounced: a class fires only if its previous frame above the threshold lies more than 1.0~s
earlier. Without the debounce, one \emph{swarm abort} would publish a burst of aborts, each
cancelling the parse path's decode again, and each counted as a separate detection. The refractory
interval is kept per class. An abort spoken immediately after a hold falls inside the hold's
interval, and it must still be published, because it is the more conservative of the two commands.
When both classes fire on the same frame, the higher score wins; neither class has priority,
because either confusion between them is fail-safe (Section~\ref{sec:membership-rule}). A trigger
cancels the decode in progress, if any, and publishes the fixed command of its class. The mapping
from the two classes to \texttt{hover} and \texttt{abort} is a constant, checked when the module is
loaded, so a third class cannot be added without changing that check. The heads are loaded only
if their files match the hashes recorded when they were trained, because the operating threshold
was selected for those weights and has no meaning for others.

\paragraph{Training the spotter.} Only the two heads are trained; the front end is the feature
models of openWakeWord's v0.5.1 release, used unchanged. Each head is a multilayer perceptron with
two hidden layers of 128 rectified linear units and a sigmoid output. The upstream trainer requires
PyTorch, which is kept out of this project's environment, so the heads are fitted with scikit-learn
and their weights written into an ONNX graph directly. The fit uses scikit-learn's Adam optimiser
with L2 regularisation of $10^{-3}$, a learning rate of $10^{-3}$, batches of 256 and at most 40
epochs, on standardised inputs and with seed 42. The corpus, synthetic positives rendered by three
\gls{tts} voices~\cite{piper} and negatives of read speech, isolated command words and hand-written
near-misses, is constructed in the \emph{M\'emoire de Master}. Training windows are labelled by
where the phrase falls, not by the clip they come from: a window that begins before the phrase and
extends past its end by a margin, 40~ms where the phrase's length was measured and 450~ms where it
was predicted from the synthesis voice's length setting, is a positive; a window containing none of
the phrase is a negative; and a window that cuts the phrase is discarded. A head is therefore
trained to fire on the complete phrase rather than on a fragment of it, but the labelling does not
fix the frame at which it fires. The time from the keyword offset, the anchor of the reflex budget,
to the first frame above the threshold is the spotter's decision delay; it is part of the reflex
latency, and Sections~\ref{sec:keyword-spotter-evaluation} and~\ref{sec:latency-experiment} report
it. Each head treats the other class as a negative. The loss weights the classes to balance, and it
weights the hand-written near-misses, 12\% of the negative clips of the training split, five times
more than other negatives; the corpus itself is unchanged. That
weighting was introduced after a first fit whose false accepts on the validation split were all
near-misses, so the held-out test split was scored twice, once for each fit.

The operating point is a single threshold for both heads, since the false-accept and false-reject
criteria describe one operating point (Table~\ref{tab:nonfunctional-requirements}). It is the
highest value on a grid, from 0.05 to 0.99 in steps of 0.01 and then 0.995, 0.998 and 0.999, at
which both classes keep a false-reject rate of at most 0.05 on the validation split: half the
budget of 0.10, as a margin for a split of 150 clips per class. The rule selected 0.999, the top of
the grid, and it was applied before the test split of the second fit was scored. The evaluation runs
the exported heads through openWakeWord in 80~ms frames, as the runtime does, and counts detections
with the same 1.0~s rule as the runtime's debounce. The rates it reports and the runtime's
behaviour therefore concern the same events, and the evaluation also verifies the export.
Section~\ref{sec:keyword-spotter-evaluation} reports those rates.

\section{Runtime}
\label{sec:runtime}
The parse path runs on the worker thread of Section~\ref{sec:audio-chain}, one utterance at a
time. For each utterance the worker reserves a sequence number from the bus, transcribes the audio,
parses the transcript, passes the result through the semantic validator and publishes it under the
number it reserved. It records the time at which each stage ends, and these timestamps are the
per-stage figures that Section~\ref{sec:latency-experiment} reports against the budget of
Table~\ref{tab:stage-budget}.

\paragraph{Speech recognition.} \texttt{whisper.cpp}~\cite{whispercpp} is run as a separate process
for each utterance, with the \texttt{tiny.en} model, three threads, and an initial prompt that lists
the command vocabulary. The invocation is defined once and shared with the dataset pipeline's
round-trip transcription, so the recogniser configuration whose errors the parser was trained on is
the one it receives transcripts from at run time. A recognition failure returns an empty
transcript, which is passed to the parser like any other rather than handled as a separate case.

\paragraph{Parser.} The language model is served by \texttt{llama-server}~\cite{llamacpp}, a
persistent process started once, with the model loaded, a single decoding slot, three threads and a
context of 512 tokens. Each parse makes three requests to it: the first renders the chat template
around the fixed system instruction and the transcript, the second tokenises the rendered text
without adding special tokens, since the template already contains them, and the third completes
the prompt under the decoding grammar, greedily and with at most 96 tokens. This is the request
sequence of the harness that measures the parser's accuracy, and the one whose tokenisation the
\emph{M\'emoire de Master} verifies against the training tokeniser. Prefill and decode times are
read from the server's own timing report rather than by timing the request, so they exclude the
client's overhead; the wall-clock time of the whole request is recorded beside them, and the
difference is the overhead of the three requests, for which the budget has no row. The validator
then runs on the worker thread, and the command is published.

\paragraph{Prompt cache.} Section~\ref{sec:dual-path} designs the fixed part of the prompt to stay
in the model's key--value cache between requests. The deployed parser does not do this: each
completion request disables the server's prompt cache, so the fixed system instruction is
processed again for every command. The reason is parity with the measurement of accuracy. The
\emph{M\'emoire de Master} scores the deployed parser with the cache disabled, and the runtime
sends the same request, so the accuracy it reports describes the parser as it runs, without an
assumption that caching leaves the decoded command unchanged; that assumption was not tested. The
cost is prefill time, since every request processes the whole prompt rather than the transcript's
tokens alone. Section~\ref{sec:latency-experiment} reports that cost as measured, against the
prefill allowance of Table~\ref{tab:stage-budget}, which assumes the cache.

\paragraph{Preemption.} A reflex-path trigger acts on the parse path from the frame-loop thread,
before its own command is published: it closes the connection of the parser's request in flight,
if there is one. The parser treats a failed request as an interrupted decode: a closed connection,
a timeout, a reply that is not \gls{json}, or an error answer to either of the first two requests.
It cannot tell a cancellation from such a fault and does not need to: no command is published for
that utterance, and the event is logged. An error answer to the completion request is not treated
so. It carries no command text, the validator resolves the empty output to a hold like any other
output it cannot accept, and the hold is published. The sequence number is
reserved when the worker takes the utterance, before transcription starts, which is the timing the
ordering rule of Section~\ref{sec:dual-path} depends on. A decode that completes despite the
cancellation therefore carries a number older than the trigger's, and the consumer discards it
(Section~\ref{sec:command-bus}). Where the trigger finds one of the parser's requests in flight, the
recovery time that the preemption-recovery criterion bounds is set by how soon the server, after
the connection closes, stops decoding and frees its slot; Section~\ref{sec:latency-experiment}
measures it for triggers that arrive during a decode. A trigger during transcription, or between
two of the parser's requests, closes nothing, and recovery then waits for the remaining stages
(Section~\ref{sec:dual-path}).

\paragraph{Core pinning.} The allocation of Table~\ref{tab:core-allocation} is applied per thread,
through the Linux affinity call, which restricts only the thread that makes it; a process started
by that thread inherits its restriction. The worker restricts itself to cores~1--3, so every
recogniser process it starts runs there. The language-model server is started from a thread
restricted to cores~1--3 for that purpose, and the same thread then restricts itself to core~0
before it runs the frame loop. The latency experiment records the affinity of every thread of the
language-model server when the server starts, and that of the frame-loop thread and of the load
thread; the worker's own restriction, and so that of the recogniser processes it starts, is applied
by the code but not recorded.

\paragraph{Artefacts from the M\'emoire de Master.} Three artefacts of the parse path are produced
by the \emph{M\'emoire de Master} and consumed here unchanged: the language-model file, Qwen2.5-0.5B
fine-tuned and quantised to Q4\_K\_M in the \gls{gguf} format; the decoding grammar; and the
one-line system instruction, identical to the one used in training and in the accuracy measurement.
The runtime adds no prompt text and no grammar rule of its own.

\paragraph{Entry point.} No entry point starts the runtime as one process. The components above,
together with the bus, the endpointer and the trained spotter, are assembled only by the harness of
the latency experiment, which builds them for its trials. The demonstration of
Section~\ref{sec:demonstration-protocol} requires such an entry point, and it is not built.

\section{Command bus}
\label{sec:command-bus}
The bus of Section~\ref{sec:dual-path} is built as one class with three operations: reserve a
sequence number, publish a message, and receive one. No separate abstract type is declared: the
interface through which Section~\ref{sec:dual-path} lets a middleware replace the bus consists of
these three operations, and a replacement would provide the same three. Each message is a single \gls{json} object
carrying the sequence number, a tag naming the path that produced it, the command's fields, and the
time of publication, and it is sent as one \gls{udp} datagram. A message longer than 4{,}096 bytes is
refused rather than split. The largest command of the schema is far shorter, so no message is ever
reassembled from fragments. The receiving side rejects a message whose path tag is neither of the
two paths. The time of publication is read from the publishing machine's monotonic clock; it is the
instant at which both latency spans of Section~\ref{sec:latency-budget} end, and it is meaningful
only on the machine that wrote it.

\paragraph{Sequence numbers.} One counter serves both paths, and it is guarded by a lock, because
the two paths publish from different threads: the reflex path from the frame loop, the parse path
from the worker. The parse path reserves its number when it takes an utterance
(Section~\ref{sec:runtime}) and passes it to the publish operation. The reflex path lets the
publish operation draw the number, because detection, construction of the command and publication
are one uninterrupted call on its side, with no interval in which a later message could be
numbered first. Numbers drawn from one counter by both paths are therefore directly comparable,
which is what the ordering rule requires.

\paragraph{Consumer.} The ordering rule is implemented in the consumer, not in the bus. The consumer
keeps the highest sequence number among the reflex-path messages it has applied. A parse-path
message with a lower number is discarded and logged; every other message is passed to the state
machine (Section~\ref{sec:state-machine}). The rule is kept out of the state machine as well as out
of the bus. Legality does not depend on which path a command came from, and a staleness check
inside the state machine would make it depend on the bus. Unit tests exercise the rule in both
directions: a parse-path message numbered before a later reflex-path message is discarded, and one
numbered after it is applied.

\paragraph{Transport as run.} The bus addresses any host, but it has run only over the loopback
interface of the Raspberry~Pi. In the latency experiment the consumer and the state machine run on
the Pi, in the same process as the runtime, rather than on the workstation of
Figure~\ref{fig:architecture}. The wireless link from the device to the workstation has therefore
never carried a command. The latency budget already places that link outside its spans
(Section~\ref{sec:latency-budget}), and Section~\ref{sec:limitations} treats its absence from the
measurements as a limitation.

\section{Flight state machine}
\label{sec:state-machine}
The state machine is one class holding the current flight state. Its five states, its transitions
and the legality of each intent are those of Section~\ref{sec:validation-layers}; the legality is
encoded once, as a table from each intent to the set of states in which it is legal, and every
decision reads that table. Every command the consumer passes on is first run through the semantic
validator by the state machine itself. The reflex path's constants are therefore validated like any
other command, and a parse-path command is validated twice, once on the device before publication
and once here.

\paragraph{Handling a command.} The state machine then applies four rules, in order. An
\texttt{unknown} command is logged and never dispatched. An abort moves the swarm to
\texttt{ABORTED} in the states where it is legal and is a logged no-op in the others. A legal
command is dispatched, and a take-off or a landing makes its transition as it is dispatched. A
command that is not legal is rejected: it becomes a hold if a hold is itself legal in the current
state, and a logged no-op otherwise. The legality of the hold is read from the same table as every
other intent's, not from a separate list of airborne states, so the rejection rule and the table
cannot disagree. Every rejection is logged with the intent rejected and the state it arrived in. The
two transitions that depend on the vehicles, reaching the take-off height and ground contact, are
separate operations, which the side that observes the vehicles calls. The reset out of
\texttt{ABORTED} is also an operation rather than a command: it receives two reports, that every
drone is on the ground and that every drone is nearly at rest, refuses the reset unless both hold,
and logs the outcome either way. No intent, from either path, reaches it.

\paragraph{Verification.} The flight-state-machine criterion is verified by an automated test of
every cell of the legality table (Table~\ref{tab:functional-requirements}). The 50 cells, five
states by ten intents, are generated as a cross product rather than listed by hand, so that no cell
can be left out. Each cell sends a complete command to a state machine in the given state and checks
three things: what is dispatched, the state afterwards and the log entry. The expected outcomes come
from a transcription of the legality table written separately from the state machine's own table,
and a further test compares the two, so that the cell tests cannot pass by reading the table they
test. A second test checks that all ten commands pass the validator unchanged, so that no cell
passes because the validator had already replaced its command with a hold. The recovery path has
its own test: all ten intents are sent to a state machine in \texttt{ABORTED}, none of them leaves
it, and only the reset does. Before the tests were accepted, three faults were introduced into the
state machine in turn, and each made tests fail. Every test of the state machine passes, the 50
cell tests among them.

\paragraph{Legality of the original intent.} The state machine reads a command's intent before it
runs the validator, keeps it for the log, and judges legality on it. When the validator replaces a
command with a hold, legality is therefore judged on the command's original intent, not on the hold
it became. On the deployed route the two never differ. The parse path validates before it publishes,
so the state machine receives the hold itself, and the reflex path publishes constants that the
validator leaves unchanged. A command that has not been validated and is handed to the state machine
directly can differ: a \texttt{set\_param} carrying no value, received during a landing, is replaced
by a hold and dispatched, although Table~\ref{tab:legality} makes a hold illegal in that state. This
is why Section~\ref{sec:safety-problem} states that no rejection can produce motion for the
deployed route only, and Section~\ref{sec:limitations} records the defect.

\paragraph{Link to the swarm controller.} The state machine does not drive the swarm controller.
Outside its tests, the only code that runs it is the consumer of the latency experiment, where it
decides what would be dispatched and drives nothing: the commands it returns reach no controller,
and the harness itself places each trial's state machine in \texttt{FLYING} before the trial starts.
Nothing reports the vehicles' height, ground contact or velocity to it. The formation-control
experiment drives the controller directly, without speech and without the state machine
(Section~\ref{sec:swarm-controller}). The demonstration of
Section~\ref{sec:demonstration-protocol} requires the link, and it is not built.

\section{Swarm controller}
\label{sec:swarm-controller}
The swarm controller receives the positions and velocities of the five vehicles and returns one
acceleration command per vehicle, every 20~ms (50~Hz). It is written against the environment
interface of Section~\ref{sec:simulation-backends} and sees nothing of either simulator beyond it.
Its only command is a formation: a shape, its size and heading, and a centre, which defaults to the
swarm's current centroid. It implements three of the six shapes the schema admits, the circle, the
line and the wedge; the other three are valid commands for which the controller has no slot
generator. No code maps the other intents, a movement, a climb, a rotation, a take-off, a landing
or a hold, onto the controller. That mapping belongs to the link from the state machine that
Section~\ref{sec:state-machine} records as not built. The controller applies no envelope of its own.
On the designed route the validator would bound every commanded value before it reached the
controller (Section~\ref{sec:validation-layers}); that route is not built, and the
formation-control experiment commands the controller directly, with a radius and a spacing that
lie inside the envelope. Nor is the envelope applied where motion happens. The backends limit speed
to 3~m/s, above the validator's ceiling of 2.0~m/s on a commanded speed, so a formation change can
move the vehicles faster than any command could set; Section~\ref{sec:limitations} returns to it.

\paragraph{Formation slots.} Each shape is generated as a set of offsets about the origin, then
rotated by the commanded heading and translated to the centre, so that a heading means the same
thing for every shape. The circle places the vehicles at equal angles on the commanded radius, and
the line spaces them evenly about the middle vehicle. The wedge puts one vehicle at the apex and the
others on two arms trailing at $30^\circ$ either side, alternating between the arms. It is then
re-centred on its own centroid: left centred on the apex, its mean position would lie behind the
commanded centre while the circle's and the line's lie on it, and the wedge would be given a longer
approach than the other two shapes for a reason unrelated to its geometry. Vehicles are assigned to
slots by minimising the total squared distance between each vehicle and its slot. A greedy
assignment, each vehicle to its nearest free slot, routinely produces crossing paths, which sends
two vehicles through the same volume. The assignment is computed once, when the formation is
commanded, and then held. Recomputed at every tick, it would let two vehicles exchange targets
whenever noise made the exchange marginally cheaper, and the pair would fly through each other.

\paragraph{Control terms.} The acceleration is the sum of three terms, in decreasing order of
authority. The first is a \gls{pid} law on the error between each vehicle and its slot, with
gains $k_p = 2.0$, $k_i = 0.05$ and $k_d = 3.0$; the derivative term acts on the vehicle's
velocity, and the integral is limited to $\pm 2.0$~m\,s against wind-up. The value of $k_d$ is
slightly above critical damping for $k_p$, which is $2\sqrt{k_p} \approx 2.83$. A formation that
overshoots its slot oscillates across the 0.5~m tolerance of the formation-accuracy criterion
during the final 5~s of a trial, the window over which that criterion is measured
(Table~\ref{tab:nonfunctional-requirements}). The second term is an artificial potential field
that repels each pair of vehicles closer than 1.5~m, with a magnitude of
$6.0\,(1/d - 1/d_0)/d^2$ for a separation $d$ and an influence distance $d_0 = 1.5$~m, and no force
beyond it. The third term is a global form of the flock-centring and velocity-matching rules of
flocking~\cite{reynolds1987}, weighted at 0.15 towards the swarm's centroid and 0.25 towards its
mean velocity. Reynolds' rules act on each vehicle's nearby flockmates; this term uses the whole
swarm, the central-force form his model avoids, which is acceptable here because the formation
slots, not flocking, organise the swarm. Flocking keeps the group together on the approach, before
the slots dominate; its collision-avoidance rule is replaced by the potential field. Once the vehicles are near their slots, the formation term determines the
trajectory and flocking contributes little. Its terms are therefore weighted low rather than
removed.

\paragraph{Separation clamp.} The potential field is a force, and a force can be outrun: with a
bounded acceleration and a finite timestep, there is a closing speed from which no force stops a
pair in time. The third mechanism of the safety problem (Section~\ref{sec:safety-problem}) is
therefore not a force but a correction of the state. After the integrator has written the new
positions, the clamp finds every pair closer than 0.80~m and moves both vehicles apart along the
line joining them, each by half the shortfall. Separating one pair can bring another pair too
close, as in a chain of three, so the clamp repeats the pass, up to 64 times, until no pair is
closer than the clamp distance. It also removes the approaching component of each such pair's
relative velocity. Without that, the pair would close again on the next tick and the clamp would
act on every tick after, which would record a resolved approach as a permanent one. Two vehicles at
exactly the same position are separated along an axis chosen from their indices, so that a trial
remains reproducible. The controller then receives the corrected state, never the uncorrected one.

The clamp distance of 0.80~m is a choice of this work: roughly twice the rotor-tip diameter of a
small quadrotor, so that the clamp acts while there is still space between the airframes. A
collision, in the collision criterion, is a pair closer than 0.35~m, strictly less than the clamp
distance, so a counted collision would mean that the clamp itself had failed. Two figures are
recorded per trial. The clamp interventions are the pairs found too close when the clamp is
entered, counted on its first pass only, so that the figure depends on the dynamics and not on how
many passes the correction takes. The collisions are counted after the clamp. This is the
mechanism the collision criterion names, zero collisions observed across all trials, backed by a
hard geometric separation clamp at the integrator, and Section~\ref{sec:formation-control}
reports both figures. The clamp rewrites the vehicles' state only on the kinematic backend, the one
that exposes its integrator; the physics simulator does not, and its runs do not apply the clamp
(Section~\ref{sec:simulation-backends}).

\section{Simulation backends}
\label{sec:simulation-backends}
The controller is written against one environment interface, and two backends implement it. The
interface has two operations. The first places the five vehicles for a given seed and returns their
positions and velocities; the second takes one acceleration command per vehicle, advances the
simulation by one control tick of 20~ms, and returns the new state. Positions are in metres and
velocities in metres per second, in a world frame with the vertical axis pointing up. The two
backends exist because speed and fidelity are different needs, and neither backend serves both.

\paragraph{Kinematic backend.} The kinematic backend treats each vehicle as a point mass whose
acceleration is commanded directly. It limits the commanded acceleration to 4~m/s$^2$ and the
speed to 3~m/s, and it treats the ground plane as impenetrable. Both limits scale the whole vector
rather than each component, so a limited command keeps its direction. The integration is
semi-implicit: the velocity is updated first, and the new velocity moves the position. The vehicles start at positions drawn, from the trial's seed, from a normal distribution of
standard deviation 0.5~m about the point $(0, 0, 2)$~m. The backend runs a 60~s trial of five
vehicles with point-mass double integration fast enough for iterative testing, which is what makes the formation-control experiment's sweep of trials
practical, and the experiment runs on it. It is also the backend whose state the separation clamp
may overwrite (Section~\ref{sec:swarm-controller}).

\paragraph{Physics backend.} The second backend runs five quadrotors in PyFlyt~0.29.0, on the Bullet
physics engine~\cite{pyflyt}, with rigid-body dynamics, rotor dynamics and PyFlyt's own attitude
control. The controller's acceleration does not reach the rotors directly. It is integrated into a
commanded velocity, subject to the same two limits as the kinematic backend, and that velocity is
sent to PyFlyt as a world-frame setpoint, which PyFlyt's inner loops then track; yaw is not
commanded. PyFlyt also accepts a position setpoint, but using it would have measured PyFlyt's own
position controller rather than the controller of Section~\ref{sec:swarm-controller}. The commanded
velocity is held by the backend rather than read back from the vehicle. PyFlyt's inner loop leaves a
small steady error in altitude, and a setpoint built on the measured velocity would feed that error
back as the next command, so that a vehicle told to hold station descends to the ground; a test guards
against that steady-state altitude droop. The physics runs at 240~Hz. A control tick is rounded to
a whole number of physics steps, five, with the setpoint held between them. Because QuadX's attitude
controller steps twice per call, each tick advances 10 physics steps (41.67~ms), so the effective
control rate is 24~Hz rather than the nominal 48~Hz or 50~Hz, and the 600 ticks evaluate 25~s of
simulated flight with the controller acting at half its nominal rate. It serves to test whether
the controller carries across to rigid-body dynamics, though transfer at the nominal 50~Hz rate is
not established (Section~\ref{sec:limitations}).

\paragraph{Cross-backend verification.} The same controller, with the same gains, runs under
both backends; nothing in it is selected per backend. That is the condition the simulation-backends
criterion rests on (Table~\ref{tab:functional-requirements}). The formation-control results come
from the kinematic backend alone. The physics backend's tests check that the same controller, with
the same gains, also brings five rigid-body quadrotors into each formation from one initial
placement; they do not reproduce the experiment's measures and apply no separation clamp. Whether
the experiment's results hold under rigid-body dynamics is therefore not established
(Section~\ref{sec:limitations}). A controller retuned for each
backend would demonstrate little about transfer: the kinematic results would then describe a controller that runs
nowhere else, and a success on the physics backend would describe a different controller. The
tests of the physics backend are written to that condition, and they place the vehicles with
seed 42. Each of the three formations is flown
for 12~s and must end with all five vehicles (the test's 85\% threshold with $N=5$) within 0.5~m of their slots, a line
formation must not sink, and one test flies the same line with the default controller on both
backends and applies the same criterion to each. All five tests pass.

\paragraph{Scope of the physics backend.} The physics backend is exercised by these tests only. It
carries no experiment, so no result reported in Chapter~\ref{chap:validation} includes rotor
dynamics. Its runs apply no separation clamp: PyFlyt owns the vehicles' state and exposes no
integrator for the clamp to correct, so on this backend only the potential field keeps the vehicles
apart. The collision criterion is therefore measured on the kinematic backend alone, and no
collision result is claimed for the physics backend.
